## 1. 개요

spendback은 온디바이스 LLM이 소비 회고를 써 주는 Android 가계부다. 지출을 폼으로 빠르게 기록하면, 한 주나 한 달이 끝났을 때 코드가 소비 지표를 계산하고 로컬 LLM이 그중 말할 사실을 골라 회고를 엮고 제안을 쓴다. 데이터와 모델은 모두 기기 안에만 있다.

- 사용자: 개발자 본인 1명(Galaxy S24+)
- 형태: React Native CLI(New Architecture) Android 앱, 포트폴리오 프로젝트
- 언어·통화: 한국어, 원화(원 단위 정수)

### 포트폴리오로 보여줄 것

1. **온디바이스 LLM 통합**: 모델 다운로드, 로드, 스트리밍, 해제
2. **LLM과 코드의 경계 설계**: LLM이 숫자를 만들 수 없는 구조를 만들고, 평가 하네스로 증명
3. **제품·UX 완성도**: 3번 탭으로 끝나는 입력, 읽히는 회고

## 2. 핵심 원칙: 계산과 사실 문장은 코드가, 사실 고르기·제안과 카테고리 추천은 LLM이

| 역할 | 담당 | 적용 시점 |
|---|---|---|
| 합산, 비율, 증감, 예산 대비, 날짜 계산, 금액 표기, 사실을 말하는 문장(문장 틀) | 코드 | MVP |
| 어떤 사실을 골라 어떤 순서로 말할지, 제안 | LLM | MVP(회고) |
| 카드 알림의 금액·가맹점·날짜·승인/취소 읽기, 전에 적은 가맹점의 카테고리 | 코드 | 2단계(카드 알림) |
| 처음 보는 가맹점의 카테고리 추천(사용자의 과거 거래를 검색해 예시로 준다) | LLM | 2단계(카드 알림) |

코드가 계산해 LLM에 넘기는 지표 묶음을 **facts**라 부른다. 원칙을 지키는 장치는 여섯 가지다.

- 회고의 사실 문장은 코드가 facts 묶음마다 써 둔 문장 틀이다. LLM은 틀의 id를 고르고, 직접 쓰는 문장은 제안 한 줄뿐이다. 틀 안의 금액, 비율, 횟수, 증감 표현과 이름은 `{키}` 플레이스홀더이고, 값은 코드가 채운다.
- LLM은 숫자를 직접 쓰지 않는다. 제안에는 카테고리·이유 태그 이름과 메모 키만 연다. 사용자가 이름에 숫자를 넣을 수 있으므로 이름도 플레이스홀더로 참조한다.
- llama.rn의 출력 문법(GBNF)으로 headline과 insight에는 틀 id만 쓰게 하고, 제안의 문자를 한글 음절과 일부 문장부호로 한정해 숫자와 facts에 없는 키를 원천 차단한다.
- 문법으로 막을 수 없는 한글 수사("삼만 원", "두 배")는 코드가 제안을 사후 검사하고, 걸리면 재생성한다.
- 직전 기간 데이터가 없으면 비교 키를 facts에 넣지 않고 비교하는 틀도 만들지 않는다. 그러면 LLM이 비교 문장을 고를 수 없다.
- 카드 알림의 카테고리 추천은 GBNF로 사용자의 보이는 지출 카테고리 이름 하나만 쓰게 하고, 코드가 id로 바꾼다. 금액·날짜·가맹점은 코드가 알림에서 읽으므로 LLM이 거래의 숫자를 만들 자리가 없다(4.9).

## 3. 범위

### MVP

- 폼 입력(지출·수입), 내역 편집·삭제
- 카테고리·이유 태그 편집
- 달력 월 예산(월 총예산 + 선택형 카테고리 예산). 한 번 정하면 다음 달에도 이어 쓴다
- 고정비 관리(항목 등록 + 달마다 기록 여부를 확인하는 체크리스트)
- 주간·월간 회고(지표, 차트, LLM 문장)
- 모델 다운로드·교체
- JSON 내보내기·가져오기
- LLM 평가 하네스(PC 로컬 스크립트)

### 2단계 이후(우선순위 순)

1. **카드 알림 파싱**: Android `NotificationListenerService` 네이티브 모듈로 카드 앱 알림을 받고, 코드가 카드사별 형식으로 금액·가맹점·날짜·승인/취소를 읽는다. 카테고리는 세 단계로 채운다. 전에 적은 가맹점이면 그때의 카테고리를 쓰고(코드), 처음 보는 가맹점이면 이름이 비슷한 과거 가맹점을 찾아 예시로 넣고 LLM이 사용자의 카테고리 하나를 고르고(검색 증강, RAG), 사용자가 폼에서 확인한 뒤 저장한다. 결제 취소 알림은 원래 거래와 짝지어 사용자의 확인을 받아 삭제한다(4.9).
2. **다짐 루프**: 회고 끝에 다음 기간 다짐을 남기고, 다음 회고에서 코드가 달성 여부를 판정한다.
3. **대화형 질의**: "이번 달 배달 얼마 썼어?" 같은 질문을 LLM이 질의로 구조화하고, 코드가 계산한다.
4. **보안**: 앱 잠금(생체 인증), DB 암호화(SQLCipher)

### 범위 밖

- 자연어 입력, 영수증 OCR, 음성 입력, CSV 가져오기
- iOS, 서버·동기화·계정, 다국어·다중 통화
- 할부, 반복 거래 자동 생성. 고정비는 자동으로 만들지 않고 체크리스트로 기록을 돕는다(4.4)

## 4. 주요 기능

### 4.1 입력(하단 시트 폼)

목표는 금액 → 카테고리 → 저장, 3번 탭이다.

| 필드 | 필수 | 규칙 |
|---|---|---|
| 금액 | 필수 | 숫자 키패드. 원 단위 양의 정수 |
| 카테고리 | 필수 | 칩 선택. 지출/수입 전환에 따라 목록이 바뀜 |
| 날짜 | 기본값 오늘 | "어제" 칩, 그 외는 날짜 선택기 |
| 지출/수입 | 기본값 지출 | 접힌 영역 |
| 이유 태그 | 선택 | 1개. 지출만 |
| 만족도 | 선택 | 후회 / 보통 / 만족. 지출만 |
| 메모 | 선택 | 과거 메모 자동완성. 같은 메모에 전에 고른 카테고리를 자동 선택(코드) |
| 결제수단 | 선택 | 카드 / 현금 / 계좌이체 |
| 고정비 | 기본값 끔 | 월세·구독 등. 회고에서 변동비와 분리. 켜면 등록한 고정비 항목을 골라 연결할 수 있다(4.4). 지출만 |

### 4.2 카테고리와 이유 태그

- 지출 카테고리 기본 11개: 식비, 카페·간식, 배달, 교통, 쇼핑, 생활, 주거·통신, 문화·여가, 의료·건강, 경조사·선물, 기타
- 수입 카테고리 기본 3개: 급여, 부수입, 기타. 월급은 급여, 부업·주식처럼 월급 밖의 수입은 부수입으로 적는다
- 이유 태그 기본 6개: 필요, 충동, 보상·스트레스, 약속·사교, 습관, 선물
- 모두 추가와 이름 변경이 가능하다. 삭제는 숨김으로 처리해 과거 거래와 집계를 보존한다.

### 4.3 예산

- 기준 기간은 달력 월(1일~말일) 하나다. 시작일 설정은 없다. 월급처럼 한 달에 한 번 들어오는 돈으로 한 달을 사는 것을 전제로 한다.
- 월 총예산을 두고, 카테고리별 예산은 선택이다.
- 예산은 한 번 정하면 다음 달에도 그대로 이어 쓴다. 바꾸면 바꾼 달부터 적용되고 지난 달의 예산은 그대로 남는다. 지난 달의 예산은 고치지 않는다(지난 회고의 기준이 바뀌지 않게).
- 예산은 변동비에만 적용한다. 고정비는 예산 사용률에 넣지 않는다. 수입(부수입 포함)은 예산을 늘리지 않는다.
- 주간 예산은 해당 주의 날짜마다 "그 달 예산 ÷ 그 달 일수"를 더해 구한다. 두 달에 걸친 주도 같은 규칙을 쓰고, 카테고리 예산도 같다.
- 주의 하루라도 예산이 없으면(첫 예산을 정한 달보다 앞선 날) 그 주의 총예산 지표를 facts에 넣지 않는다. 카테고리 예산도 카테고리마다 같아서, 두 달에 걸친 주에서 한 달에만 그 카테고리 예산이 있으면 그 카테고리의 주간 예산 지표를 뺀다. 반쪽 예산과 한 주 지출을 비교하면 사용률이 부풀려진다(2장의 "데이터가 없으면 키를 넣지 않는다"와 같다).
- 홈에서는 진행 중인 달의 예산 소진율과 남은 일수 대비 소비 속도를 보여준다. 계산은 아래와 같고 금액은 원 단위로 내린다.

| 값 | 식 |
|---|---|
| 사용액 | 이번 달 1일부터 오늘까지의 변동비 지출 합계(오늘 기록 포함) |
| 남은 예산 | 월 총예산 − 사용액. 0보다 작으면 초과 상태이고 초과액을 보여준다 |
| 남은 일수 | 말일 − 오늘 + 1. 오늘은 아직 쓸 수 있는 날이라 포함한다 |
| 하루 쓸 수 있는 금액 | 남은 예산 ÷ 남은 일수. 초과 상태에서는 보여주지 않는다 |
| 지난 비율(게이지 기준선) | 오늘 ÷ 그 달 일수. 오늘이 끝날 때까지의 몫이라 1일에도 0이 아니다 |
| 사용률 | 사용액 ÷ 월 총예산. 지난 비율보다 크면 빠르게 쓰고 있는 것이다 |

### 4.4 고정비

월세, 통신비, 구독처럼 매달 나가는 지출을 항목으로 등록해 두고, 달마다 기록했는지 확인한다. 목적은 입력 편의보다 누락 방지다(13장).

- 항목에는 이름, 예상 금액, 지출 카테고리, 결제일(매월 N일), 결제수단(선택)을 둔다.
- 주기는 매월 하나다. 연 단위 결제(보험 연납 등)는 항목으로 두지 않고, 결제한 달에 고정비를 켜서 입력한다.
- 결제일이 그 달에 없으면(2월 30일 등) 그 달의 말일로 본다.
- 등록 전에 이미 지난 결제일을 미기록으로 잡지 않도록, 항목은 등록한 날(당일 포함) 이후의 결제일부터 확인한다. 등록 전 결제일이라도 그 달에 항목에 연결한 거래가 있으면 기록한 것으로 센다(이미 낸 달을 등록 뒤에 기록하는 경우).
- 해지하면 항목을 숨긴다. 숨긴 항목은 확인하지 않고, 4.2와 같이 과거 거래와 집계는 보존한다.
- 거래를 자동으로 만들지 않는다(13장). 예상 금액은 입력 폼의 기본값으로만 쓰고, 지표와 예산은 기록된 거래로만 계산한다.

**체크리스트**

- 한 달 안에 항목에 연결된 거래(`fixedCostId`)가 1건 이상 있으면 그 달은 기록한 것으로 본다.
- 홈에는 이번 달 기록 현황("고정비 3/5 기록")과, 결제일이 오늘이거나 지났는데 기록하지 않은 항목을 보여준다.
- 항목을 누르면 입력 폼이 채워진 채로 열린다. 금액·카테고리·결제수단은 항목 값, 메모는 항목 이름, 날짜는 그 달의 결제일이다. 사용자는 금액을 확인하고 저장하며, 저장한 거래는 그 항목에 연결된다.
- 입력 폼에서 고정비를 켜고 항목을 골라도 연결된다(4.1).
- 끝난 달의 월간 회고를 생성하기 전에, 그 달에 기록하지 않은 항목이 있으면 먼저 알린다(4.6).

### 4.5 내역

날짜별로 묶은 목록, 필터(기간 / 카테고리 / 태그 / 지출·수입), 편집·삭제.

### 4.6 회고

**기간**: 주간(월~일)과 월간(달력 월). 비교 대상인 직전 기간은 바로 앞 주, 바로 앞 달이다.

**생성 조건**

- 끝난 기간만 생성한다. 진행 중인 기간은 지표와 차트만 보여준다.
- 기간 안의 변동비 지출 기록이 3건 미만이면 LLM을 부르지 않고 "기록이 부족해요"라고 안내한다.
- 끝난 기간의 회고 상세를 처음 열 때 생성해 저장한다. 저장본이 있으면 저장본을 보여주고, 재생성은 사용자가 요청할 때만 한다.
- 월간 회고는 생성하기 전에(저장본이 없거나 재생성을 요청했을 때) 그 달에 기록하지 않은 고정비 항목이 있는지 확인한다(4.4). 있으면 그 항목을 보여주고, 사용자는 기록하거나 그대로 생성할 수 있다.
- 한 기간에 회고는 1개만 둔다. 재생성에 성공하면 기존 회고를 덮어쓴다.
- 생성은 스트리밍으로 보여주고, 생성 중 취소를 지원한다. 스트리밍 단위는 문장 필드(`headline`, 각 `insights` 항목, `suggestion`)다. 필드 하나가 완성될 때마다 코드가 틀 id를 문장으로 펼치고 사후 검사를 해, 통과한 필드만 플레이스홀더를 채워 화면에 내보낸다. headline은 틀 id 몇 토큰이라 프롬프트 처리가 끝나면 바로 나온다. 사후 검사에 걸리면 화면에 나간 문장을 지우고 "다시 쓰는 중" 상태로 전체를 재생성한다.

**facts(코드 계산)**

"대상" 열은 지표를 계산할 때 쓰는 지출이다. 고정비는 월세처럼 특정 날짜에 몰려 주간 비교와 최대 단일 지출 같은 지표를 왜곡하므로, 총지출과 수입 대비 지출률을 뺀 지표는 변동비만 쓴다.

| 지표 | 대상 | 주간 | 월간 |
|---|---|---|---|
| 총지출(전체, 변동비, 고정비를 따로) | 전체 | O | O |
| 직전 기간 대비 증감액·증감률 | 변동비 | O | O |
| 카테고리별 합계·비중, 증감 상위 3개 | 변동비 | O | O |
| 예산 대비 사용률, 초과·잔여 금액(총예산·카테고리 예산) | 변동비 | O(일할 예산) | O |
| 이유 태그별 합계·비중 | 변동비 | O | O |
| "후회" 만족도가 붙은 지출 합계 | 변동비 | O | O |
| 최대 단일 지출 | 변동비 | O | O |
| 무지출일 수(변동비 지출이 없는 날) | 변동비 | O | O |
| 지출이 가장 많은 요일 | 변동비 | O(가장 많이 쓴 날) | O |
| 같은 메모가 반복된 지출 상위 3개(메모 완전 일치 기준) | 변동비 | O | O |
| 수입 대비 지출률(그 달에 수입 기록이 있을 때만) | 전체 | - | O |

회고는 끝난 기간만 다루므로 "남은 일수 대비 소비 속도"는 회고 지표가 아니라 홈 지표다.

- 직전 기간과 비교하는 지표(증감액·증감률, 증감 상위 3개)는 직전 기간 전체가 첫 기록일(가장 이른 거래의 날짜) 이후일 때만 facts에 넣는다. 직전 기간이 기록을 시작한 날과 겹치면(첫 기록일이 직전 기간의 첫날이어도) 없음으로 본다. 반쪽 기간과 비교하면 증감이 부풀려진다.
- 증감 상위 3개는 증감액의 절댓값이 큰 순이다. 같으면 이번 기간 금액이 큰 순, 그다음 카테고리 순서다. 증감이 0인 카테고리는 넣지 않는다.
- 직전 금액이 0이면 증감률 키를 넣지 않는다(비율을 정할 수 없다). 증감액은 넣는다.
- 무지출일은 첫 기록일부터 센다. 기록을 시작하기 전의 날은 쓰지 않은 날이 아니라 기록하지 않은 날이다.
- 월간의 "지출이 가장 많은 요일"은 요일별 합계로 고른다. 주간의 가장 많이 쓴 날과 최대 단일 지출은 같으면 이른 날이다.
- 반복 메모 상위 3개는 횟수 순, 같으면 합계 순이다.

**출력 형식**

LLM은 아래 JSON만 출력한다. `headline`과 `insights`는 코드가 써 둔 문장 틀의 id이고, `insights`는 2~4개다. LLM이 직접 쓰는 문장은 `suggestion` 하나다.

```json
{ "headline": "category.3.change", "insights": ["tag.2.amount_share", "budget.usage_balance"], "suggestion": "다음 주에는 ... 보세요." }
```

코드는 id를 틀로 펼쳐 `{ "headline": "...", "insights": [{ "about": "category.3", "text": "..." }], "suggestion": "..." }`로 저장한다. `text`는 플레이스홀더가 든 틀이고 렌더러가 채운다. 묶음과 키 이름 규칙은 `src/retro/keys.ts`에, 문장 틀은 `src/retro/frames.ts`에 둔다. 증감과 예산 잔액은 방향까지 코드가 쓴 서술어 값("32,400원 늘었어요")이다.

- 문장 틀은 facts 묶음마다 코드가 쓴다. 틀 안의 수치, 증감, 카테고리·이유 태그 이름은 플레이스홀더이고, 이름 키는 표시 이름이 아니라 id로 만든다(`{category.<id>.name}`). 예를 들어 틀 `category.3.change_share`는 `{category.3.name} 지출이 지난주보다 {category.3.change_phrase}. 변동비의 {category.3.share}{을/를} 차지했어요.`이고, 코드가 `배달 지출이 지난주보다 29,000원 늘었어요. 변동비의 36%를 차지했어요.`로 채운다. 데이터가 없는 사실은 틀도 없다.
- 증감 방향도 계산 결과이므로 "늘었어요 / 줄었어요 / 같았어요"까지 코드가 채운다. 값에 맞는 말도 코드가 고른다(같으면 "지난주와 같았어요", 총예산이 남으면 "전체 예산이 …남았어요", 넘으면 "전체 예산을 …넘었어요", 수입보다 많이 쓰면 "수입보다 …더 썼어요"). 총예산은 "전체 예산"이라 쓴다. 카테고리 예산 문장("배달 예산의 71%를 써서 …") 뒤에 "예산이 …"가 오면 같은 예산으로 읽혔다.
- 코드가 묶음마다 눈에 띄는 정도와 그 까닭이 된 키(focus)를 정하고, 그 순서로 프롬프트에 쓴다. 적자, 예산 초과, 카테고리 예산 초과, 큰 증감, 한 카테고리 몰림, 무지출일이 많은 주가 앞에 온다. 정도는 같은 기간 변동비에 대한 비율로 정해 주간·월간에 같이 쓴다(`src/retro/keys.ts`).
- 요청할 때마다 틀 id와 이름 키로 GBNF 문법을 만든다. headline은 앞 묶음 셋의 틀 중 채운 뒤 30자 안의 한 문장이고 그 묶음의 까닭을 말하는 틀에서 고른다. insight는 headline과 다른 묶음의 틀에서 고르고, 총지출 묶음은 쓰지 않는다. 회고 상세의 카드가 총지출·변동비·고정비와 변동비 증감을 늘 보여 주기 때문이다. 총지출 묶음은 headline 후보로만 남고, 회고 문장(대개 headline)이 변동비 증감을 말하면 카드는 비교 줄을 뺀다. 총지출을 뺀 묶음이 셋보다 적으면 insight 2개를 다른 묶음으로 채울 수 없어 총지출도 쓴다. 제안은 "다음 주에는"(월간은 "다음 달에는")으로 시작해 "세요."로 끝나고, 사이는 여섯 글자까지의 한글 낱말을 공백이나 쉼표로 잇는다(화이트리스트). 숫자를 빼는 블랙리스트 방식은 다른 문자 체계의 숫자와 기호로 우회된다(13장).
- 한 묶음의 틀은 회고에 하나만 쓴다. 같은 묶음의 틀은 같은 값을 되풀이하므로("전체 예산이 92,700원 남았어요."와 "전체 예산의 67%를 써서 92,700원 남았어요.") 앞 insight와 묶음이 같은 insight는 코드가 버리고, 남은 insight가 2개보다 적으면 재생성한다. 틀은 그 묶음의 키만 쓰므로 다른 사실의 키를 붙이는 오용(10장)이 생기지 않는다.
- 제안의 플레이스홀더는 카테고리·이유 태그 이름과 메모 키만 2개까지 쓸 수 있다. 금액·비율 같은 값은 쓰지 않는다. 늘었·줄었·증가·감소처럼 증감을 직접 쓰는 낱말로 시작하지 못하게 하고(늘려·줄여·줄이는 쓸 수 있다), 플레이스홀더 다음 낱말은 원·번·일 같은 단위 글자로 시작할 수 없다.
- 플레이스홀더 바로 뒤의 조사는 틀과 제안 모두 쌍으로 쓰고(`{이/가}`, `{을/를}`, `{은/는}`, `{와/과}`, `{으로/로}`, `{이에요/예요}`, `{이었어요/였어요}` 등) 코드가 채운 값의 마지막 글자 받침으로 고른다(`으로/로`는 ㄹ 받침도 `로`). 숫자와 기호로 끝나는 값은 읽는 소리로 판단한다(`18%`는 "퍼센트"라 받침이 없다). 제안의 문법은 플레이스홀더 바로 뒤에 맨 조사를 쓰지 못하게 한다. 스파이크의 "54,000원였어요" 같은 오류를 구조로 막는다.
- 사후 검사는 제안에 한다. 한글 수사와 단위의 조합("삼만 원", "두 배", "세 번" 등), 분수·몫·할·옛 수사·날수("삼분의 일", "팔할", "석 달", "엿새"), 숫자 없이 남은 단위("지출이 원 늘었어요"), 증감을 직접 쓴 말, 같은 글자 되풀이("요요요"), 채운 뒤 45자를 넘는 길이가 나오면 재생성한다. 틀은 코드가 써서 검사에 걸리지 않는다. 재시도는 최대 2회이고, 그래도 실패하면 폴백으로 넘어간다. 시드는 시도마다 바꾸고, "다시 만들기"가 같은 문장을 내지 않게 첫 시드는 무작위다.
- 금액은 어디서나 `32,000원` 형식으로 표기하고, 비율은 정수 %로 표기하고 사사오입한다(17.5% → 18%). 음수는 절댓값 기준이다(-17.5% → -18%). 규칙은 코드에 두고 단위 테스트로 고정한다.

**저장**: facts 스냅샷, 출력 JSON, 모델 ID, 프롬프트 버전, 생성 시각을 함께 저장한다. 과거 회고는 목록에서 다시 열람할 수 있다.

**톤**: 담백한 분석가. 마지막에 제안 한 줄을 붙인다.

**폴백**: LLM으로 문장을 만들 수 없으면 코드가 틀을 골라 보여주고, 원인에 따라 다르게 안내한다. headline은 headline 후보의 첫 틀(가장 눈에 띄는 묶음의 까닭을 말하는 틀)이고, insight는 다른 묶음에서 묶음마다 하나씩(그 묶음의 까닭을 쓴 틀이 있으면 그 틀) 3개까지 쓴다. 눈에 띄는 순서로 고르되, headline이나 앞 insight와 종류가 같은 묶음(카테고리 여럿 등)은 다른 종류를 먼저 고른 뒤에 채운다. 같은 모양의 문장("배달·쇼핑·생활 지출이 지난주보다 …")이 이어지지 않게 하려는 것이다. 후회한 지출과 이유 태그는 틀 모양이 같아("…은 …원으로 변동비의 …%였어요") 한 종류로 본다. 보이는 순서는 눈에 띄는 순서다. 총지출 묶음을 빼는 규칙은 insight와 같다. 제안은 LLM이 쓰는 문장이라 없다(`src/retro/frames.ts` pickFrames).

| 원인 | 안내 | 동작 |
|---|---|---|
| 모델이 없음 | "모델이 없어 앱이 고른 사실만 보여 줘요" | 모델 관리로 이동 |
| 모델 로드 실패 | "모델을 불러오지 못해 앱이 고른 사실만 보여 줘요" | 다시 시도, 모델 관리로 이동 |
| 사후 검사 반복 실패 | "회고를 엮지 못해 앱이 고른 사실만 보여 줘요" | 다시 만들기 |

폴백 상태는 회고로 저장하지 않는다. 다음에 상세를 열면 다시 생성을 시도한다. 저장본이 있는 기간에서 다시 만들기가 실패하면 저장본을 그대로 보이고 "다시 만들지 못해 저장한 회고를 보여 줘요"라고 안내한다. 재생성은 성공했을 때만 덮어쓴다(생성 조건).

### 4.7 모델 관리(설정)

- 레지스트리에 등록된 모델 목록을 보여주고, 다운로드, 삭제, 사용 모델 선택을 지원한다.
- 다운로드는 Hugging Face에서 받는다. 진행률 표시, 이어받기, SHA-256 검증, 저장 공간 확인을 붙이고 Wi-Fi 사용을 권장한다. 받는 중에는 `.part` 파일에 쓰고 Range로 이어받으며, 받으면서 SHA-256을 계산해 맞을 때만 모델 파일로 옮긴다. 남은 크기와 여유 64MB가 없으면 시작하지 않는다. 앱 전용 Turbo Native Module(`src/native`, OkHttp)이 맡아 화면을 나가도 이어진다.
- 개발 빌드에는 기기의 로컬 파일 경로에서 모델을 로드하는 옵션을 둔다.

### 4.8 백업

JSON 내보내기·가져오기. 내보내기는 Android 공유 시트로 보내고, 가져오기는 시스템 파일 선택기로 고른다. 가져올 때 스키마 버전을 확인하고 Zod로 검증한다. 고정비 항목도 함께 담고, 거래의 `fixedCostId` 연결을 유지한다.

가져오기는 병합하지 않고 전체 교체한다. 확인 대화상자를 거치고, 파일 전체를 먼저 검증한 뒤 한 트랜잭션으로 바꿔서 도중에 실패하면 기존 데이터가 그대로 남는다. 교체 직전의 데이터는 앱 안에 한 벌(가장 최근 것만) 보관해, 잘못 가져왔을 때 백업 화면에서 한 번 되돌릴 수 있다.

거래의 가맹점과 추천값(4.9)도 담는다(백업 버전 2). 버전 1 파일은 두 값이 없는 것으로 읽는다. 카드 알림 대기열은 기기에서 받은 알림을 처리하는 줄이라 설정처럼 넣지 않는다.

### 4.9 카드 알림(2단계)

카드 앱의 결제 알림으로 기록을 돕는다. 거래를 자동으로 저장하지 않는다. 알림은 홈의 대기 목록에 쌓이고, 사용자가 폼에서 확인한 뒤 저장한다(4.4의 "자동으로 만들지 않는다"와 같다).

**받기**

- 지원하는 카드사 앱의 알림만 연다. 다른 앱의 알림은 내용을 읽지 않는다. 지원 카드사와 알림 형식은 사용자의 실제 알림 샘플로 정한다(`src/cards/parse.ts`, 11장).
- 네이티브 서비스는 원문을 앱 내부 저장소의 대기열에 적기만 한다. 읽기·짝짓기·추천은 앱이 앞으로 올 때 JS가 한다. 서비스가 다시 연결되면 알림창에 남은 카드 알림을 한 번 훑어 끊긴 동안 온 것을 줍는다. 같은 알림은 지문(카드 앱 + 원문)으로 한 번만 받는다.
- 코드가 카드사별 형식으로 종류(승인·취소), 금액, 가맹점, 날짜를 읽는다. 날짜는 알림 문구의 월·일이고, 연도는 받은 시각으로 정한다(받은 달보다 뒤의 달이면 지난해). 형식에 맞지 않는 알림은 버리지 않고 원문과 함께 "읽지 못한 알림"으로 보여 준다. 카드사가 문구를 바꾸면 바로 드러난다.

**대기 목록(홈)**

- 항목은 가맹점, 금액, 날짜, 추천 카테고리를 보인다. 누르면 입력 폼이 채워진 채로 열린다. 금액과 날짜는 알림 값, 결제수단은 카드, 메모는 가맹점 이름이고, 카테고리는 추천값을 고른 채 "추천"을 표시한다. 이유 태그와 만족도는 비운다. 회고의 재료라 사람이 고르는 값이다.
- 저장하면 거래에 가맹점 원문과 추천값을 함께 남긴다. "기록 안 함"을 고르면 항목을 치운다.
- 같은 날 같은 금액의 지출이 이미 있으면 "이미 기록했을 수 있어요"를 붙인다. 손으로 적었거나 고정비 체크리스트로 기록한 거래와 겹치지 않게 한다. 자동으로 치우지는 않는다.

**카테고리 추천**

1. 정확 일치(코드): 정규화한 가맹점 이름이 전에 저장한 거래의 가맹점과 같으면 가장 최근 거래의 카테고리를 쓴다. LLM을 부르지 않는다.
2. 검색 + LLM: 처음 보는 가맹점만 다룬다. 이름이 비슷한 과거 가맹점 5곳과 그 카테고리를 찾아 예시로 넣고, LLM이 사용자의 보이는 지출 카테고리 중 하나를 고른다. 문법(GBNF)이 카테고리 이름만 쓰게 하고 코드가 id로 바꾼다. LLM은 가맹점이 무엇인지(세상 지식)는 알지만, 사용자가 그런 지출을 어디에 적는지(개인 습관)는 모른다. 그 습관을 검색한 예시로 준다.
3. 사람: 폼에서 확인하거나 고쳐 저장한다. 저장한 거래는 다음 검색 자료가 된다.

- 가맹점 정규화는 유니코드 정규화(NFC), 공백 정리, 법인 표기(`(주)`, `㈜`, `주식회사`) 지우기, 영문 대문자다. 지점명은 지우지 않는다.
- 검색은 이름을 글자 두 개씩 자른 조각의 겹침이다. 조각은 띄어쓰기를 넘지 않는다. 조각마다 사용자의 가맹점 중 몇 곳에 나오는지로 가중치(IDF)를 줘, 지점명처럼 흔한 조각의 무게를 낮춘다. 가중치가 없으면 "교촌치킨 역삼점"이 "BBQ치킨"(치킨)보다 "스타벅스 역삼점"(역삼, 삼점)에 가깝다. 한 사람의 가맹점은 많아야 수천 곳이라 임베딩 모델과 벡터 DB를 쓰지 않는다. 검색은 함수 하나(`findSimilar`)로 감싸, 글자 비교로 못 잡는 경우가 실제로 보이면 그 함수만 바꾼다(13장).
- 처음 보는 가맹점의 추천은 홈이 보이는 동안 한꺼번에 돌리고, 끝나면 모델을 내린다(6장 실행 정책). 모델이 없으면 추천 없이 카테고리를 비운다.
- 정확도는 추천을 고치지 않고 저장한 비율이다. 설정의 카드 알림 화면에 정확 일치와 LLM 추천을 따로 보여 준다.

**결제 취소**

정규화한 가맹점과 금액으로 승인과 짝짓는다.

1. 대기 중인 승인(같은 카드 앱)과 짝이 맞으면 둘 다 치운다. 저장한 것이 없어 잃는 기록이 없다.
2. 저장한 거래(가맹점 원문이 있고, 취소일 전 90일 안, 최근 것부터)와 짝이 맞으면 "9월 28일 스타벅스 4,500원 기록을 지울까요?"를 띄우고, 사용자가 지운다.
3. 짝이 없으면(부분 취소, 금액을 고친 거래, 알림을 받기 전에 결제한 것) "짝을 찾지 못한 취소"로 보여 주고, 사용자가 내역에서 고치거나 넘긴다.

같은 가맹점·금액의 거래가 둘이면 짝이 틀릴 수 있어 저장한 거래는 묻고 지운다(13장).

**권한**

설정의 "카드 알림"에서 무엇을 읽는지(지원 카드사 앱의 알림만, 기기 밖으로 나가지 않는다) 설명하고, 시스템의 알림 접근 화면으로 보낸다(Android 11 이상은 이 앱의 토글로 바로 간다). 돌아오면 허용 여부를 다시 확인한다. 앱이 직접 알림을 띄우지는 않는다(13장).

## 5. 화면 구성

탭은 3개다. 설정은 탭이 아니라 홈 헤더 오른쪽의 톱니 버튼으로 여는 화면이다.

| 탭 | 내용 |
|---|---|
| 홈 | 이번 달 예산 게이지(총예산·카테고리), 소비 속도, 고정비 체크리스트, 카드 알림 대기 목록(4.9), 최근 지출, 입력 버튼(하단 시트 폼을 연다). 헤더 오른쪽에 설정 |
| 내역 | 목록, 필터, 편집·삭제 |
| 회고 | 주간/월간 목록 → 상세(스트리밍 문장, 카테고리 도넛 차트, 일별 막대 차트) |

설정 화면에는 카테고리·태그 편집, 예산, 고정비 항목, 카드 알림(권한, 추천 정확도), 모델 관리, 백업을 둔다. 예산은 홈 게이지와 첫 실행 버튼, 고정비는 홈 고정비 줄, 모델 관리는 회고 폴백에서도 들어간다.

### 실행 정책

- 회고 상세 화면에서 문장을 생성해야 할 때(저장본이 없거나 재생성을 요청했을 때)만 로드하고, 화면을 나가거나 앱이 백그라운드로 가면 해제한다. 회고 목록, 진행 중인 기간, 기록이 부족한 기간, 저장본을 여는 경우에는 로드하지 않는다.
- 카드 알림의 카테고리 추천(4.9)은 처음 보는 가맹점이 대기 목록에 있을 때 홈(과 그 위 입력 폼)에서 로드해 한꺼번에 돌린다. 다 돌았거나, 회고 탭으로 가거나, 앱이 백그라운드로 가면 해제한다. 모델은 한 번에 한 벌만 메모리에 둔다. 추천은 분류라 온도 0으로 고른다.
- 추론 모드(thinking)는 끄고, 스트리밍과 취소를 지원한다. Qwen3.5는 추론 모드를 꺼도 출력 앞에 빈 `<think></think>`가 붙으므로 떼고 파싱한다.
- 스레드는 6개로 둔다(스파이크에서 2·4·6·8개 중 가장 빨랐다). 컨텍스트 길이와 샘플링은 평가 하네스로 정한다(11장).
- llama.rn 0.12.9의 `ignore_eos`와 `logit_bias`는 쓰지 않는다. 비운 벡터에 토큰 id를 인덱스로 써서 앱이 SIGSEGV로 죽는다(`cpp/jsi/JSIParams.cpp:629`). 버전을 올릴 때 다시 확인한다.
- 생성 중에 해제할 때는 생성을 멈추고 끝나기를 기다린 뒤 해제한다. 생성 중인 컨텍스트를 바로 해제하면 네이티브 생성 스레드가 해제된 컨텍스트를 읽어 앱이 SIGSEGV로 죽는다(2026-10-02 에뮬레이터, 프롬프트 처리 중 취소). 다시 만들기는 앞 모델을 내린 뒤 올린다(모델 두 벌이 메모리에 오르지 않게). llama.rn 0.12.9의 `stopCompletion`은 타입과 달리 Promise를 돌려주지 않는다.

### 인터페이스

- 회고 문장 생성은 `narrate(facts)` 인터페이스 뒤에 둔다. 구현은 llama.rn 구현과 가짜 구현 두 가지이고, 도메인·화면 테스트는 가짜 구현으로 돌린다.
- 프롬프트는 버전으로 관리하고, 회고 스냅샷에 그 버전을 기록한다.
- 카드 알림의 카테고리 추천은 `suggestCategory`(`src/cards`) 뒤에 둔다. 정확 일치와 검색은 코드이고, 모델을 부르는 부분은 회고와 같은 `Generate`로 받는다. 검색은 `findSimilar` 하나다.

### 평가 하네스(PC 로컬 스크립트, CI 아님)

- node-llama-cpp로 폰과 같은 GGUF 파일, 프롬프트, GBNF 문법을 쓴다. Windows와 macOS 양쪽에서 돈다.
- 입력은 고정된 facts 스냅샷 약 20개다. 직전 기간 없음, 기록 적음, 예산 초과, 고정비 비중이 큼 같은 경계 사례를 포함한다.
- 자동 점검 항목: 스키마 통과, 참조한 키가 facts에 있는지, 숫자·한글 수사가 없는지, 문장 길이, 금지어, 문장 품질 휴리스틱(증감 낱말 깨뜨리기·동의어, 수사 누출, 프롬프트 옮겨 쓰기, 해요체 아님, 다짐·질문, 되풀이·뭉친 낱말, 다른 사실에 이름 붙이기, 같은 묶음), 사실 고르기(스냅샷마다 정한 꼭 말해야 할 사실을 놓쳤는지, 첫 사실을 headline으로 골랐는지)
- 프롬프트 토큰과 생성 토큰을 세어 스파이크의 S24+ 속도로 폰 시간을 추정한다. 프롬프트 버전을 바꿔 돌릴 수 있고, 저장한 결과를 지금의 점검으로 다시 세어 같은 잣대로 비교한다
- 문장 길이 한도(플레이스홀더를 채운 뒤, 공백 포함): headline 30자, insight 60자, suggestion 45자. headline과 suggestion은 한 문장, insight는 두 문장까지다. S24+에서 본문 한 줄이 약 22자라 headline은 두 줄(xl), insight는 세 줄, suggestion은 두 줄에 맞춘 값이다. 문장 틀은 이 한도 안에 들도록 코드가 만든다
- 금지어 초안: 느낌표, 인사·호칭("안녕하세요", "여러분", "고객님"), 단정·과장("항상", "절대", "완벽", "최고", "최악", "대박", "심각"), 비난·훈계("낭비", "과소비", "한심", "반성", "해야 해요"), 사실 밖 추측("것 같아요", "나 봐요", "듯해요")
- 길이 한도와 금지어는 첫 하네스 결과를 보고 조정한다
- 사람 채점 항목: 자연스러움, 고른 사실이 적절한지, 톤. 채점 기준표를 둔다.
- 결과로 모델 비교표를 만들어 README에 싣는다.
- 카드 알림의 카테고리 추천도 같은 GGUF로 비교한다(`scripts/eval`). 습관이 일관된 가상 사용자의 과거 가맹점과, 처음 보는 가맹점을 세 종류(글자가 겹치고 습관을 따름, 글자는 안 겹치지만 습관을 따름, 세상 지식으로 충분함)로 준다. 검색 없음, 비슷한 가맹점 5곳, 여기에 카테고리별 대표 가맹점, LLM 없이 가장 가까운 가맹점의 카테고리를 종류별 정답률로 비교한다. 정답을 만든 쪽이 데이터도 만들었다는 한계가 있어, 실제 정확도는 앱의 "추천 그대로 저장" 비율로 본다.

## 7. 데이터 모델(초안)

금액은 원 단위 정수다. id는 SQLite 정수 자동 증가 키다. 날짜는 기기 로컬 시간 기준 `YYYY-MM-DD` 문자열이고, 한 주의 시작은 월요일이다.

| 엔티티 | 주요 필드 |
|---|---|
| Transaction | id, type(expense·income), amount, date, categoryId, reasonTagId?, satisfaction?(regret·neutral·satisfied), memo?, paymentMethod?(card·cash·transfer), isFixed, fixedCostId?(isFixed인 거래만), merchant?(카드 알림의 가맹점 원문. 정규화는 비교할 때 한다), suggestedCategoryId?, suggestionSource?(exact·llm), createdAt, updatedAt |
| CardInbox(카드 알림 대기열) | id, fingerprint(카드 앱 + 원문, unique), app(패키지명), kind(approval·cancel·unreadable), amount?, merchant?, date?, text(원문), postedAt, status(pending·done·dismissed), suggestedCategoryId?, suggestionSource?, pairedTransactionId?(취소가 짝지은 거래), createdAt. 처리한 항목은 중복을 거르는 데만 쓰고 90일 뒤 지운다. 백업에 넣지 않는다(4.8) |
| Category | id, type(expense·income), name, sortOrder, hidden, isDefault |
| ReasonTag | id, name, sortOrder, hidden, isDefault |
| Budget | effectiveFrom(`YYYY-MM`), total, categoryBudgets(`[{ categoryId, amount }]`, 예산을 정한 카테고리만, JSON 열). 한 달의 예산은 effectiveFrom이 그 달 이하인 것 중 가장 늦은 것이다. 예산을 바꾸면 그 달을 effectiveFrom으로 저장한다(4.3) |
| FixedCost | id, name, amount(예상 금액), categoryId(지출), dayOfMonth(1~31), paymentMethod?, sortOrder, hidden, createdAt, updatedAt |
| Retrospective | id, kind(weekly·monthly), periodStart, periodEnd, facts, output, modelId, promptVersion, createdAt. (kind, periodStart)마다 1개 |
| Model(앱에 내장한 레지스트리) | id, repo, commit, fileName, sizeBytes, sha256, license. 값은 6장 레지스트리 표를 따른다 |
| 설정(SQLite `settings` 표) | 키-값(JSON). 사용 모델 ID. 받은 모델은 파일로 판단한다(크기가 맞으면 받은 것) |

**참고할 옆 폴더 프로젝트**

- `../expo-plate`: pnpm, husky, commitlint, CI, `.claude/rules` 구성을 참고한다. Expo 기반이라 템플릿으로 쓰지는 않는다.
- `../rn-upgrade-kit`: RN 업그레이드 스킬 모음이다. Expo를 쓰지 않는다는 전제가 spendback과 맞는다. 그중 `rehearsal`은 Windows에서 실행을 거부하므로 macOS에서 쓴다.
- `../design-system`: `@eeennsu/{tokens,web,native}`의 원본이다. native는 NativeWind와 react-native-css를 peer로 정확히 고정하고, react와 RN은 범위(react ≥19, RN ≥0.81)로 받는다. 원본 레포에서 로컬 링크로 검증할 때는 react·RN 버전이 정확히 같아야 한다(`../design-system/CLAUDE.md`). spendback에 필요해 만든 0.3.0(Chip, Icon, RN 눌림 표시·누름 영역·입력 포커스, 번들 크기 줄이기)은 2026-09-25에 publish했고 spendback이 쓴다(DESIGN.md 5.2).

## 9. 테스트 전략

- **단위(Jest)**: 지표 계산기, 예산 일할과 이어 쓰기, 홈 소비 속도, 고정비 체크리스트 판정(말일, 등록일 경계), 날짜와 주 경계, 금액 포맷터, 플레이스홀더 렌더러(조사 고르기 포함), GBNF 생성기, 한글 수사 검사기, 백업 스키마(버전 1 읽기 포함), 카드 알림 읽기(카드사별 샘플), 가맹점 정규화와 이름 조각 검색, 정확 일치, 카테고리 문법, 취소 짝짓기. 핵심 원칙을 지키는 부분이라 TDD로 만든다. 마이그레이션 SQL은 Node 내장 SQLite(Node 22.13 이상)로 적용해 기본값을 확인한다.
- **컴포넌트(RNTL 14)**: 입력 폼의 3번 탭 흐름, 회고 화면의 상태(생성 중 / 완료 / 폴백 / 기록 부족 / 고정비 미기록 알림)
- **E2E(Maestro)**: 입력 → 내역 → 회고 열람. `.maestro/record.yaml`(빈 앱에서 기록 → 홈·내역 반영 → 고치기 → 지우기)과 `.maestro/retro.yaml`(개발 빌드의 샘플 데이터 → 끝난 주의 회고 상세 → 모델 없음 폴백 → 모델 관리)이다. 둘 다 `clearState`로 시작해 받은 모델 파일도 지운다. 모델이 있는 기기의 생성은 수동으로 본다(DESIGN.md 1.8). 디버그 빌드를 설치하고 Metro를 켠 뒤 `pnpm e2e`로 돌린다. Maestro CLI(2.11.0, Java 17)는 맥에서 `curl -fsSL https://get.maestro.mobile.dev | bash`, Windows에서 GitHub 릴리스의 `maestro.zip`을 `~/.maestro`에 풀어 설치하고, 두 곳 모두 `~/.maestro/bin`을 PATH에 넣는다. 사용 통계는 `~/.maestro/analytics.json`의 `enabled`를 false로 끈다(또는 `MAESTRO_CLI_NO_ANALYTICS=1`). 카드 알림은 개발 빌드만 `com.android.shell`의 알림도 카드 앱으로 받아, 에뮬레이터에서 `adb shell cmd notification post`로 흉내 낸다
- **LLM**: 평가 하네스(6장)

## 10. 위험과 가정

| 위험·가정 | 대응 |
|---|---|
| CPU 추론만 가능해 느리다. 스파이크(스레드 6)에서 첫 회고의 headline까지 Qwen 8.6~11.3초, Kanana 13.7~18.7초, EXAONE 6.2~8.5초, 전체는 18~31초가 걸렸다. 대부분 약 600~850토큰 프롬프트 처리 시간이다. 모델을 올린 동안 메모리는 PSS 기준 2.0~3.3GB다. 회고 파이프라인의 프롬프트는 이보다 길다(첫 프롬프트 1,540~1,640토큰, 문장 틀 1,250~1,360토큰). 토큰 수와 스파이크 속도로 추정하면 v4의 첫 문장은 Qwen 14초, Kanana 27초, 전체는 Qwen 17초, Kanana 31초다(2026-10-02, 실기기 미측정). x86_64 에뮬레이터에서는 프롬프트 처리만 수 분이 걸려 속도를 잴 수 없다 | facts 표현을 압축해 프롬프트를 줄이고, 생성 중 상태를 보여준다. 문장 틀은 LLM이 id만 써서 생성 토큰이 약 60~80개다 |

## 13. 결정 기록

| 결정 | 이유 |
|---|---|
| 입력은 폼만 둔다(자연어 입력 제외) | 금액과 카테고리 같은 정형 입력은 폼이 자연어보다 빠르고, 자연어 파서는 구현 난이도만 높인다. LLM의 입력 도움은 카드 알림의 카테고리 추천(4.9)에서 보여 준다 |
| GBNF의 문장 문자는 화이트리스트로 정한다 | 2026-09-24 스파이크에서 숫자만 뺀 블랙리스트 문법은 9회 중 5회가 `۱۱۲`(아랍·페르시아 숫자), `⅔`, `₁`, `㎡`, `％`로 숫자를 썼고, `ㄴ만` 같은 자모나 태국어·한자·영어로도 빠져나갔다. 한글 음절과 일부 문장부호만 허용한 문법에서는 9회 모두 숫자와 외국 문자가 없었다 |
| 숫자는 플레이스홀더로만 쓴다 | 사후 검증과 달리 "LLM은 숫자 문자를 쓸 수 없다"가 문법으로 구조적으로 보장되고, 테스트로 증명할 수 있다. 문법으로 막을 수 없는 한글 수사는 사후 검사와 재생성으로 막는다. 증감 방향도 계산 결과라서 코드가 쓴다 |
| 기준 기간을 달력 월 하나로 통일한다 | 월간 회고를 달력 기준으로 정했기 때문에, 예산 주기와 어긋나지 않도록 시작일 설정을 없앴다 |
| 완전 로컬로 만든다 | "금융 데이터가 기기 밖으로 나가지 않는다"가 로컬 LLM의 설득력이다. 서버를 붙이면 범위가 두 배가 된다 |
| Android만 지원한다 | 사용자 본인 폰(S24+) 전용이다 |
| 런타임은 llama.rn | New Architecture를 네이티브로 지원하면서 JSON 스키마·GBNF 제약 디코딩을 하는 사실상 유일한 크로스 플랫폼 런타임이다. Gemini Nano는 대상 기기에서 쓸 수 없고, ExecuTorch는 제약 디코딩이 없다 |
| 회고는 끝난 기간만 만든다 | 진행 중인 데이터로 결론을 내리지 않는다 |
| 폴백은 코드가 고른 틀 문장을 보여준다(2026-10-03) | 처음에는 지표와 차트만 보였다. 템플릿 문장 생성기를 따로 만들면 문장 생성기가 두 벌이 되기 때문이었다. 문장 틀이 생겨 폴백도 같은 틀과 눈에 띄는 순서(`src/retro/keys.ts`)를 쓰므로 생성기는 하나다. 모델을 받지 않았거나 생성에 실패해도 회고 문장이 있고, 빠지는 것은 LLM의 고르기와 제안이다 |
| 금액 표기를 `32,000원`으로 통일한다 | 화면마다 표기가 달라지지 않게 한다 |
| React Native 0.87.x를 유지한다 | 2026-09-24 기준 0.88은 RC(0.88.0-rc.2)이고 정식 버전은 0.87.1이다. 0.88이 정식 출시되고 패치가 나온 뒤 `../rn-upgrade-kit`로 올린다 |
| 고정비는 대부분의 회고 지표와 예산에서 뺀다 | 월세처럼 특정 날짜에 몰리는 지출이 주간 비교, 최대 단일 지출, 예산 일할을 왜곡한다 |
